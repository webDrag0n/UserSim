### 1. 智能体驱动机制详细阐述（文档更新）

#### 1.1 用户 Agent 文档（[02-user-agent.md](02-user-agent.md) 新增第 8 节）

**新增内容**：
- **8.1 大模型驱动（LLM-driven）**：
  - 机制：通过 prompt 注入 30 个人格面 + 结构化喜好，LLM 推理生成对话和决策
  - 优势：表达自然、人格交互隐式建模、开发成本低
  - 劣势：非确定性、可控性弱、测试困难、有推理成本
  - 当前实现：`llm_user.py` 的 prompt v2

- **8.2 规则规划器驱动（Rule-based planner）**：
  - 机制：确定性规则映射状态到行为（压力阈值 → 求助概率，模板库抽取对话）
  - 优势：完全确定、可解释、0 LLM 成本
  - 劣势：表达单调、规则爆炸、人格交互需手写
  - 当前实现：`scripted.py` 三档脚本用户

- **8.3 混合路径（未来方向）**：
  - 规则规划器生成意图 + LLM 负责表达（解耦推理与表达）

- **8.4 规则规划器的图结构分析**（核心修正）：
  - **修正判定**：用户 Agent 是多目标优化系统，**可以构成图结构**
  - **5 节点图结构**：
    - N1: 更新需求状态（饥饿/社交/刺激/成就）
    - N2: 计算驱动力曲线（hunger: u=[(1-x)/0.6]^1.5, stimulation: 倒U曲线等）
    - N3: 生物钟调制（饭点增强饥饿驱动、深夜增强睡眠需求）
    - N4: 综合求助倾向（多个需求汇合）
    - N5: 人格调节（神经质/外向性/宜人性影响决策）
  - **回边**：事件执行后需求满足，触发状态反馈重新计算
  - **图结构特征**：多源汇合、非单调映射（倒U曲线）、状态反馈、时间依赖（生物钟）

#### 1.2 助手 Agent 文档（[03-assistant-agent.md](03-assistant-agent.md) 新增第 7 节）

**新增内容**：
- **7.1 大模型驱动（当前实现）**：
  - LLM 一次性输出观测（`user_belief`）+ 控制（`tool_calls`）+ 对话（`reply`）
  - 优势：上下文整合强、共情自然、快速原型
  - 劣势：估计不稳定、控制策略隐式、有校准刻度泄漏（已知问题）

- **7.2 规则规划器驱动（脚本助手）**：
  - 观测器：带噪声估计（σ 随时间衰减）+ 滞后模拟
  - 控制器：按增益 K 选择最佳恢复变体（good 档最优控制，mid 档超调，poor 档不足）

- **7.3 混合路径（Phase 2 提议架构）**：
  - LLM 观测器 → 定性判断 → 规则积分器 → 数值 x̂ → 规则控制器 → 恢复意图 → LLM 执行器

- **7.4 规则图结构的可行性分析**：
  - **8 节点 DAG 结构**：N1 解析对话 → N2 估计状态 → N3 更新画像 → N4 检查干预条件 → N5 选择恢复类型 → N6 选择时段与变体 → N7 生成回复意图 → N8 LLM 渲染
  - **回边**：N6 失败（冲突/余额不足）→ N5 换类型，N5 穷尽 → N7 无法安排
  - **与 HTN 关系**：简化的单层 HTN
  - **用户 vs 助手对比**：
    - 优化目标：4 个需求 vs 4 个状态维度
    - 决策类型：反应式 vs 前瞻性规划
    - 图深度：~5 节点 vs ~8 节点
    - 回边语义：状态反馈 vs 重新规划

### 2. 系统差异深度分析

通过 Agent 对代码库的深入分析，完成了当前实现与目标设计的详细对比（见 [14-user-driven-planning.md](14-user-driven-planning.md) 第 0 节）：

**已实现**：
- 熵增（饥饿/疲劳/无聊持续增长）
- 需求动力学（4 个需求 + 驱动力曲线 + 满足曲线）
- Session 框架（用户可主动结束）
- 时间推进机制

**部分实现**：
- 生物钟（只有饭点，无完整昼夜节律）
- 事件库（全局唯一，非个性化）
- Session 结束标准（有 `max_turns_per_session=20` 强制截断）

**完全缺失**：
- 天气系统（无状态、无马尔可夫转移）
- 用户主动规划（当前是助手创建事件，用户被动响应）
- 用户意图（session 无意图驱动）
- 用户记忆（无跨 session 记忆）

**设计偏差**：
- **触发方向反了**：目标是"用户根据需求主动规划 → 进入事件 → 开 session"，当前是"世界概率性生成 `assist_prompt` → 用户被动响应"
- **能力倒置**：目标是"用户有主动事件库、自己规划"，当前是"助手有候选清单、助手创建事件"

## 二、核心洞察

### 1. 用户 Agent 不是简单的反应式系统

**原有误解**：用户 Agent 只做"反应式表达"（感知 → 表达），不需要图结构。

**修正认识**：用户 Agent 是**多目标优化系统**，包含：
- **需求动力学**：4 个需求（饥饿/社交/刺激/成就），各有独立的驱动力曲线
- **生物钟调制**：饭点增强饥饿驱动、深夜增强睡眠需求
- **非单调映射**：刺激需求的倒 U 曲线（太少无聊、太多过载）
- **状态反馈**：需求满足后重新计算驱动力（回边）

因此用户 Agent 同样适合用图结构建模，只是图较浅（~5 节点）。

### 2. 用户 vs 助手的本质差异

| 维度 | 用户 Agent | 助手 Agent |
|---|---|---|
| 优化目标 | 4 个需求（饥饿/社交/刺激/成就） | 4 个状态维度（valence/energy/satiety/stress） |
| 决策类型 | 需求驱动的反应式决策 | 前瞻性多步规划 |
| 图深度 | ~5 个节点 | ~8 个节点 |
| 回边语义 | 状态反馈（需求满足） | 重新规划（冲突处理） |

两者都是多目标优化系统，都适合用图结构建模，只是图的复杂度和回边语义不同。

### 3. 当前系统的核心架构问题

**触发方向反了**：
- **目标设计**：用户根据需求主动规划 → 创建意图事件 → 逐个进入事件开 session
- **当前实现**：世界概率性生成 `assist_prompt` → 用户被动响应 → 助手创建事件

**能力倒置**：
- **目标设计**：用户有主动事件库、自己决定要做什么
- **当前实现**：助手有候选清单、助手创建事件、用户只能请求

这是一个**范式级别的差异**，需要重构 Runner 主循环和 Agent 职责划分。
